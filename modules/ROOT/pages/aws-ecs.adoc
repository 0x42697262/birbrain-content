= AWS ECS

Elastic Container Service: runs containers.
Regional.

* https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html[ECS developer guide]

== pieces

[cols="1,3"]
|===
| Piece | What

| cluster | a namespace for services and tasks; empty clusters cost nothing
| task definition | the recipe: images, CPU/memory, env, secrets, ports, logs, health checks. Versioned: `family:revision`
| task | one running copy of a task definition
| service | keeps N tasks running, replaces failed ones, rolls out new revisions
| Fargate | AWS runs the host; you pay per task vCPU and GB
|===

== cluster

----
$ aws ecs create-cluster --cluster-name c --capacity-providers FARGATE \
  --settings name=containerInsights,value=disabled
----

Container Insights adds CloudWatch metrics at extra cost.

== task definition

Key fields for Fargate:

[source,json]
----
{
  "family": "app",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "runtimePlatform": {"cpuArchitecture": "ARM64", "operatingSystemFamily": "LINUX"},
  "cpu": "256",
  "memory": "512",
  "executionRoleArn": "arn:aws:iam::<account-id>:role/app-ecs-execution",
  "containerDefinitions": [ ... ]
}
----

* `cpu` `256` = 0.25 vCPU; `memory` in MiB. Only certain pairs are valid.
* `ARM64` (Graviton) is cheaper; the image must be built for `linux/arm64`.
* `awsvpc`: each task gets its own network interface. All containers in a task share `localhost`.

Per container:

* `essential: true` = if this container stops, the whole task stops.
* `dependsOn` + `condition: HEALTHY` = start only after another container passes its health check.
* `healthCheck` runs *inside* the container, so the command must exist in the image (`CMD` form, exit 0 = healthy).
* `environment` for plain values, `secrets` for values from SSM or Secrets Manager (see xref:aws-ssm-parameter-store.adoc[]).
* `logConfiguration` with `awslogs` sends stdout/stderr to xref:aws-cloudwatch-logs.adoc[CloudWatch Logs].

----
$ aws ecs register-task-definition --cli-input-json file://td.json
$ aws ecs describe-task-definition --task-definition app --query taskDefinition
$ aws ecs list-task-definitions --family-prefix app
----

Every register creates a new revision.
Old revisions stay until deregistered and deleted:

----
$ aws ecs deregister-task-definition --task-definition app:1
$ aws ecs delete-task-definitions --task-definitions app:1
----

== execution role vs task role

*Execution role*: used by ECS itself to start the task.
Pull from ECR, read `secrets`, write logs.
Managed policy `AmazonECSTaskExecutionRolePolicy` + `ssm:GetParameters` for SSM secrets.

*Task role*: used by your code inside the container to call AWS APIs.
Not needed if the app never calls AWS.

* https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task_execution_IAM_role.html[Task execution IAM role]
* https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-iam-roles.html[Task IAM role]

== service

----
$ aws ecs create-service --cluster c --service-name s \
  --task-definition app --desired-count 1 --launch-type FARGATE \
  --deployment-configuration 'minimumHealthyPercent=0,maximumPercent=100,deploymentCircuitBreaker={enable=true,rollback=true}' \
  --network-configuration "awsvpcConfiguration={subnets=[subnet-a,subnet-b],securityGroups=[sg-x],assignPublicIp=ENABLED}"
----

Deployment settings, as % of desired count:

* `maximumPercent` = how many tasks may run during a deploy. `200` starts the new task before stopping the old one.
* `minimumHealthyPercent` = how low it may drop. `0` allows stopping the old task first.
* `0`/`100` = never two tasks at once. Needed when state lives in memory; costs a short outage per deploy.
* Circuit breaker with rollback = a deploy that never gets healthy returns to the last good revision.

Networking:

* public subnet + `assignPublicIp=ENABLED` = the task can reach ECR, SSM, logs and the internet without a NAT gateway.
* private subnet = needs a NAT gateway or VPC endpoints, otherwise `ResourceInitializationError`.

Common operations:

----
$ aws ecs update-service --cluster c --service s --desired-count 0       # stop, keep everything
$ aws ecs update-service --cluster c --service s --desired-count 1       # start
$ aws ecs update-service --cluster c --service s --force-new-deployment  # restart, re-read secrets
$ aws ecs update-service --cluster c --service s --task-definition app:5 # roll to a revision
----

Status:

----
$ aws ecs describe-services --cluster c --services s \
  --query 'services[0].[desiredCount,runningCount,deployments[0].rolloutState]'
$ aws ecs describe-services --cluster c --services s --query 'services[0].events[:5].message'
----

Task and container state:

----
$ aws ecs list-tasks --cluster c --service-name s
$ aws ecs describe-tasks --cluster c --tasks <task-arn> \
  --query 'tasks[0].[lastStatus,healthStatus,stoppedReason,containers[].[name,lastStatus,healthStatus,reason]]'
----

Delete:

----
$ aws ecs update-service --cluster c --service s --desired-count 0
$ aws ecs delete-service --cluster c --service s --force
$ aws ecs delete-cluster --cluster c
----

== deploy from github actions

Pattern: build image, push to xref:aws-ecr.adoc[ECR], fetch the current task definition, swap the image, register and update the service.

* `aws-actions/configure-aws-credentials` (OIDC, see xref:aws-iam.adoc[])
* `aws-actions/amazon-ecr-login`
* `aws-actions/amazon-ecs-render-task-definition`
* `aws-actions/amazon-ecs-deploy-task-definition`

Fetching the task definition from AWS keeps account-specific ARNs out of the repo.
Full workflow: xref:日記:2026-11-13.adoc[2026-11-13].
